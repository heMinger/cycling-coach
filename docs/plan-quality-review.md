## 为什么原计划容易模板化

1. 计划流程没有读取知识库。问答链的向量检索对计划流程不生效。
2. 三份知识文件以指标解释和固定规则为主，没有针对目标、训练基础、可用时间、完成情况的选择过程。
3. 强制状态输出围绕 TSB 分区和每周 TSS 上限，容易让模型把负荷模型当作恢复诊断。
4. 档案写死 FTP、体重与已过期目标，又叠加实时字段；备用档案包含旧示例周训练，造成冲突。
5. 计划是自由文本和任意 load_target，缺少可计算步骤；时长、瓦数、负荷没有一致性检查。
6. 历史对话未传入计划流程，用户的近期纠正不一定生效。
7. 前端读取错误的响应层级；聊天生成的计划没有返回给计划面板。

## 原始代码复现

用受控模型响应运行原始函数，非真实模型实验：
- 输入非法 JSON：run_state_analysis 返回 tss_limit=400、正常训练周、无限制强度。
- 输入过去日期和 900 TSS 的课程，即使状态提示上限为 100：run_plan_generation 原样返回。

这些结果证明流程有缺陷，不表示实际模型一定会生成同样的错误。

## 本轮改进

- 新增 planning.py：完整知识卡片输入、近期对话、明确日期窗口与用户约束；输出草案或待补充信息。
- 当前知识库很小，计划流程直接读取全部完整卡片；保留结论与局限，避免 Top-3 小片段遗漏。未来内容变大再做主题筛选/检索，并保持完整卡片。
- 重写三个知识文件，新增训练分配和课程选择两份卡片。区分研究结论、设计建议与示例课程。没有声称示例课程经过直接实验验证。
- 每节课输出目的、步骤、调整条件、来源 ID；程序计算分钟和确认 FTP 对应的瓦数。
- 校验日期窗口、重复日期、总/单日时间、不可训练日期、步骤数字与来源 ID。仅尝试一次修复；仍不合格则不返回可写入计划。
- 写入日历前重新校验、从结构化步骤重建描述，不相信客户端自由文本或 load_target。
- 步骤负荷代理值不是实际 NP/TSS，不写入日历目标 TSS。
- 去掉写死的个人档案与过期示例记录；缓存/断连状态显式标注，当前版本不基于缓存自动生成可执行课程。
- 清除页面写死的旧 FTP/目标与“已读取数据”欢迎语，避免界面与真实状态不一致。
- 主流程以 Strava 提供活动记录，Intervals 的 activity_days=0 时不再获取当天活动，避免重复展示。
- 对话与计划面板共享草案响应，保存生成结果供后续修改；展示假设、问题和完整依据。
- 版本化知识索引，避免改完知识库仍检索到旧集合；用户静态档案不再混入通用知识索引。

## 尚未验证或解决

- 模型是否真正选择合适课程、理解疼痛/疲劳、合理分配强度，必须真实运行并人工审核。
- ID 校验只能防止引用不存在的卡片，不能证明每项建议被该研究支持。
- 自由文本约束的语义遵循依赖模型；要强制约束日期和时间，请使用结构化表单。
- 未支持强度、FTP/CP和个体反应的完整训练模型；未实现真实训练后的自适应复评。
- 日历多事件写入仍非事务操作，失败后需检查部分写入；跨请求幂等、账户鉴权和多人数据隔离仍是后续工作。
- API /plan/create 改为接收 plan 与 constraints；前后端必须同时更新。
- 知识摘要依据本次对话中检索的公开摘要/可获取全文，不是穷尽性系统综述。

## 如何验证真实模型

在本地环境或 .env 配置 DEEPSEEK_API_KEY，不要把密钥提交仓库。

```sh
python evaluations/run.py --live --output evaluations/latest.json
```

仅使用合成资料，不读取真实训练平台、不写日历。六个场景：稳定训练者的时间预算、新手资料不足、疼痛与正 TSB 冲突、因工作漏课、过期目标、陈旧缓存。

每个场景核查：是否遵守时间/日程；课程是否与经验匹配；目的是否具体；恢复安排是否合理；引用是否支持该原则；不确定性是否表达正确。状态匹配仅是辅助检查，不能当作训练质量评分。
